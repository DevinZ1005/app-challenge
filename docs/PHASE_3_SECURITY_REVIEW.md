# Phase 3 focused security review

Reviewed locally before migration 008 is applied to staging. Scope: migrations 001–008, the Phase 1 identity/authorization path, Phase 3 API validation and database access, application/audit permissions, and the corresponding tests. No remote database was queried or changed. Existing uncommitted Phase 3 work was preserved.

Conclusion: the revised migration 008 is ready for controlled staging validation. No administrator authorization bypass or automatic provider-access grant was found in the reviewed workflow. Four classes of input-integrity defects were reproduced and corrected locally. This review does not certify the permissions of a remote database that was not inspected.

## Findings fixed

1. **Non-finite verification dates:** PostgreSQL accepted `-infinity` as an earlier contact date. A direct administrator RPC could therefore store a value that is not a usable date and could break date rendering. The constraint now requires a finite AD timestamp, no later than the database-assigned review timestamp. BC dates are also rejected, avoiding PostgreSQL date strings unsupported by the UI. The shared API schema rejects year zero.
2. **Malformed evidence URLs:** the original authority pattern allowed `https://?claimed-proof`, `https://#claimed-proof` and literal backslashes. The constraint now requires a nonempty authority without query/fragment delimiters, user-info, whitespace or backslashes, and rejects literal backslashes in the path as well. Shared validation applies the same structural restriction and retains URL-parser checks. This is syntax validation, not a network lookup or proof that the website is official.
3. **Meaningless phone evidence:** punctuation-only values such as `-------` passed the old phone character check. Phone evidence now requires 7–15 ASCII digits in addition to the existing character and length restrictions. Email evidence remains an alternative. Boundary tests accept valid 7- and 15-digit examples.
4. **Whitespace-only review explanations:** PostgreSQL `btrim` removed ordinary spaces but left tabs/newlines and some Unicode whitespace. Direct administrator RPCs could satisfy the minimum length with a blank explanation. Notes now normalize leading/trailing whitespace before validation and storage; the table also requires normalized notes. The trim pattern explicitly covers ECMAScript whitespace, including NBSP and BOM, which the POSIX class alone did not reject in the local tests.

These defects were reachable through a direct **administrator** RPC; they did not let anonymous applicants or ordinary users become administrators. The first regression run reproduced ten accepted invalid inputs, and a later Unicode test exposed two further whitespace variants. All are rejected by the final implementation, without a decision or audit entry being left behind.

## Requirement-by-requirement result

| Requirement                                                     | Result and evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Authenticated administrators only                            | API identity derives role from `administrators` and approved `provider_users` records, ignoring claimed role metadata and failing closed on query errors. The RPC independently checks `public.is_admin()`. Tests deny anonymous, authenticated-without-subject, ordinary, approved-provider, forged-metadata and revoked-administrator contexts.                                                                                                                                                                                                               |
| 2. No direct table-update bypass                                | PantryFit administrators use the normal `authenticated` database role; migration 008 revokes application mutation privileges and supplies no write RLS policy. Tests verify denied direct writes, including truncation. A privileged fixture-only update separately proves that the trigger still guards history. Database owners remain trusted operators, not ordinary PantryFit users.                                                                                                                                                                       |
| 3. Private data and review decisions inaccessible to non-admins | Migration 007 grants application SELECT only to `authenticated`, with administrator-only SELECT RLS. Migration 008 preserves it. Anonymous SELECT is denied, ordinary and provider SELECT returns no application rows, and review attempts are denied before reading an application.                                                                                                                                                                                                                                                                            |
| 4. Reviewer and time cannot be forged                           | No caller-supplied reviewer/timestamp parameters exist. The trigger assigns `auth.uid()` and `statement_timestamp()`. A fixture supplies a different administrator UUID and old timestamp; the stored values are overwritten with the real caller and statement time. Strict API validation rejects extra privilege fields.                                                                                                                                                                                                                                     |
| 5. Audit records cannot be rewritten                            | Migration 001 revokes application-role table privileges and grants authenticated audit SELECT only, with administrator/own-actor read RLS. There is no audit write policy. Tests deny INSERT, UPDATE, DELETE and TRUNCATE for anonymous, ordinary, provider and administrator application sessions, including a log visible to its ordinary actor.                                                                                                                                                                                                              |
| 6. Competing decisions cannot both succeed                      | The RPC locks the application using `SELECT ... FOR UPDATE`, then checks its current status. The trigger checks the transition again. The local competing-call test produces one decision and one audit record. PGlite queues statements, so this is not a test with independent concurrent connections; see the staging checkpoint below.                                                                                                                                                                                                                      |
| 7. Final decisions cannot be repeated                           | Both the RPC and trigger reject any update once status is final. Tests cover repeated/opposing decisions after approval and rejection, including another administrator and attempted history edits.                                                                                                                                                                                                                                                                                                                                                             |
| 8. Approval grants no access                                    | The approval code mutates only the application and its audit record. No Auth account or invitation API is called, and no invitation table/function is introduced. Tests compare all fixture Auth users, administrator records, memberships, organizations and program count before/after approval. An existing ordinary applicant still has no organization access afterwards.                                                                                                                                                                                  |
| 9. SECURITY DEFINER safety                                      | Both new functions use `pg_catalog,pg_temp`; tables and authorization helpers are schema-qualified. The helper is not executable by application roles. PUBLIC/anonymous RPC execution is revoked, and authenticated RPC execution remains subject to the internal administrator check. Tests inspect function metadata and prove that hostile public-schema overloads and temporary table names are not used. The inherited `is_admin()` function uses qualified `public.administrators` and `auth.uid()` and reads only current-user administrator membership. |
| 10. Required verification evidence                              | Approval requires explicit true affiliation confirmation, an HTTPS source, phone/email method, matching contact syntax, and a finite supported non-future contact timestamp. Rejection cannot carry approval evidence. Invalid evidence rolls back all changes. Independent verification remains an administrator's real-world responsibility; neither a URL nor a checkbox proves the contact happened.                                                                                                                                                        |
| 11. Existing pending application remains valid                  | Tests create an application through the Phase 2 RPC before applying 008, then compare every original column afterwards and check that new review fields are NULL. The partial unique index continues to prevent duplicate pending applications and allows a fresh application after a final decision. The actual staging row was not accessed.                                                                                                                                                                                                                  |
| 12. Malicious input and rollback                                | Tests cover invalid/null decisions, SQL-looking strings treated as data, self-review, malformed evidence, unsupported dates, Unicode whitespace, modified applicant fields, final-history updates, hostile search paths and forced audit-storage failure. A failed audit insert leaves the application pending with no review metadata or new audit record.                                                                                                                                                                                                     |

The locking analysis follows PostgreSQL's documented behavior: a waiting `FOR UPDATE` obtains the updated row after the first transaction completes; stronger isolation can instead return a serialization failure, which the API maps to a conflict. See [PostgreSQL row-level locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS).

The function search paths, revoked PUBLIC execution and transactional creation/grants follow [PostgreSQL SECURITY DEFINER guidance](https://www.postgresql.org/docs/current/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY). Required evidence has explicit non-NULL checks, avoiding the fact that a [CHECK expression returning NULL is accepted](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS).
