## Product brief and scope

PantryFit helps Bronx households compare food assistance with their schedule, equipment, refrigeration and diet, while showing uncertainty. Providers propose changes; administrators review publication and separately record verification. The immediate milestone is a small, verified bilingual pilot in ZIP 10468. A successful result is a household understanding which service to confirm next; a compatibility score does not guarantee food, eligibility or travel time.

This handoff interprets “every app needs” as a baseline of product, usability, security, data, quality, and operational capabilities, followed by features conditional on the business model. There is no universal feature list that makes arbitrary software complete. The matrix is a repository audit and implementation handoff, not security certification or evidence of deployment.

Conditional modules must be reviewed rather than automatically added. Payments require billing/refund/webhook work only when money moves. Accounts require recovery, invitations and revocation only for the roles that sign in. User uploads require file validation/storage controls only when uploads exist. Notifications require delivery/preferences/unsubscribe when enabled. Offline functionality requires a safe freshness model. Jurisdiction, age group, business model and data practices determine any policy review. None of these is satisfied merely by adding a generic page.

## Repository audit and completed remediation

The authoritative item-level matrix is [`launch-checklist.json`](launch-checklist.json): each entry records status, reason, owner, code evidence, acceptance and whether it blocks public launch. `implemented` means source and relevant checks are present, with execution results in `VERIFICATION.md`; `pending` means work or proof remains; `not-applicable` means an explicit scope decision. File existence alone never proves behavior.

Existing strengths: strict TypeScript; deterministic matcher; anonymous household flow; English/Spanish dictionary; responsive navigation; accessible form labels; uncertainty and fictional-data disclosures; admin publication workflow; Zod validation; RLS and transaction tests; import validation; privacy page and feedback.

Added in this review:

- A bounded 64 KiB JSON reader on all JSON mutation endpoints. Malformed JSON returns 400, unsupported content type 415, and oversized requests 413. Limits inspect streamed bytes, including requests without trustworthy Content-Length.
- Consistent noncached API errors with request IDs, sanitized unexpected-failure events and Retry-After for throttled requests. Errors do not echo exception messages or user content.
- Production configuration that fails closed without a complete Supabase configuration. A production fictional demo requires explicit `PANTRYFIT_ALLOW_DEMO=true`.
- Loading, route-error and root-error recovery; request-failure handling for admin review/logout/listing/verification; a failed provider fetch clears listings rather than displaying embedded fictional data.
- Cross-platform temporary storage paths; scripts use Playwright's managed browser by default.
- A baseline enforcing CSP, private API cache headers, robots exclusion, and a readiness endpoint that reads the public data dependency.
- CI for locked installation, production dependency audit, types, lint, tests, build and browser/accessibility checks; scheduled dependency PR configuration; a repeatable handoff integrity check.

Distributed throttling, full session lifecycle, production monitoring, backups and real data verification remain open. No live account, paid service, external message, tracking SDK or real provider claim was created.

## Pilot acceptance and measurement

Proposed initial targets for founder approval: at least 8 of 10 pilot participants complete the matching task without assistance; at least 8 of 10 correctly distinguish a known conflict from unknown information; every published pilot service has documented source and verification ownership; no unresolved access-control defect or critical accessibility barrier. Small samples are directional and must not be described as population-level evidence.

Record aggregate task success, failure reason, time to useful result, freshness coverage, and confirmed referral outcome when participants consent. Do not record household questionnaire answers, precise location, immigration/income details or names in analytics. Keep research notes in a team-controlled, consent-governed system rather than this repository. No impact claims exist yet.

For capacity, load-test the agreed pilot peak plus a reasonable buffer against staging using synthetic data, and record p95 latency, error rate, database connections and estimated spend. Set a capacity limit from observed results. Measure mobile performance on the production build; field Web Vitals require real traffic and a separate privacy-reviewed collection decision.

## Handoff protocol for the next engineer or coding agent

1. Read this file, `launch-checklist.json`, `VERIFICATION.md`, `SECURITY.md`, `OPERATIONS.md` and applicable repository instructions. Inspect current code before trusting any status. Never treat a prior report as proof for changed code.
2. Run `npm ci`, `npm run check`, `npm audit --omit=dev --audit-level=high`, `npx playwright install chromium`, `npm run test:e2e`, and `npm run test:production`. Run `npm run test:a11y` with a local demo server for the additional authenticated/questionnaire states. Use an isolated fictional dataset.
3. For every matrix item, inspect the cited implementation and exercise its acceptance criteria. If a required capability is missing, implement the smallest suitable change, add a meaningful regression test, and rerun affected checks. Do not add unrelated conditional features to inflate completeness.
4. Keep evidence and verification date current. Record actual commands/results and environment limitations in `VERIFICATION.md`. A new manual release decision needs durable staging/test evidence, not a changed checklist label.
5. For work needing project access, real data, contacts or human review, record the exact dependency, owner and acceptance evidence. Never fabricate verified listings, legal policies, credentials, monitoring configuration or approvals.
6. Run `npm run readiness:release`. It must currently fail because public-launch evidence is incomplete. Fix all listed blockers, rerun full checks, and obtain founder go/no-go before changing the launch decision. The checker never grants release approval.

Suggested next-agent instruction: “Act as PantryFit's engineering owner. Follow docs/HANDOFF.md, audit every requirement in docs/launch-checklist.json against current code, implement missing applicable capabilities with regression coverage, and update evidence and verification results. Preserve anonymous household privacy and fictional labels. Report unresolved external dependencies honestly. Do not mark manual launch gates complete without recorded evidence.”
